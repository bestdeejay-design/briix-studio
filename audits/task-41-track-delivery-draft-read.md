# Поставка: fix(#41) — трек доезжает до ушей, черновики в чате читаются, а не редактируются

**Ветка:** `feat/draft-read-track-delivery` · **База:** `feat/compact-chat-ui` (60081de, поверх #40/#35)
**Задача:** находки владельца 21.11 — «ошибка на конце длинных генераций, трек не послушать»,
«промт и лирика в чате должны быть не полями для редактирования, а разворачивающейся строкой
для чтения с копированием целиком; правки — в тонкой настройке».
**Связанные:** briix-studio#35 (UI v2, один фокус — создание музыки), #40 (промт через мозг).

## Что сделано

### 1. Длинные генерации больше не умирают «на конце»

Три связанные причины в `studio.js`:

- **60-секундный потолок на весь файл.** `fetchWithTimeout(FILE_TIMEOUT_MS=60000)`
  рвал загрузку по суммарному времени, без учёта прогресса: длинный трек (десятки МБ,
  pro) не успевал, хотя канал был жив. Ошибка выглядела как «генерация упала» — на самом
  деле падала загрузка готового файла.
- **Карточка рендерилась только после полного блоба.** `createMusic` ждал
  `await fileBlob(...)` до рендера: сбой загрузки убивал карточку целиком — готовый трек
  исчезал из сессии (джоба на сервере есть, файла в ленте нет).
- **Таймаут не ретраился** (остальные ошибки — ретраились).

Механика после правки:

- `fetchBlobStream` — потоковая загрузка (`response.body.getReader()`), таймаут
  «по простою»: **90 с на первые байты** (сервер может собирать M4A из WAV по контракту
  `?refetch=1` — на длинных треках это небыстро) и **45 с между порциями данных**;
  дедлайн отодвигается с каждым чанком — живой канал не убивается;
- два разных отказа: молчащий сервер (0 байт) — честная ошибка сразу, без ретраев;
  обрыв на середине (`progressed`) — транзиентный, до 3 попыток внутри слота;
- `createMusic`: карточка трека рендерится **сразу по ready** (обложка-PLAY, волна,
  меню «⋯»), блоб грузится лениво через `loadBlob: () => fileBlob(...)`; у карточки
  уже был ретрай «нажмите на обложку — попробуем ещё раз» — теперь он первый рубеж;
  `feedPush`/`libAdd` уходят сразу за ready, не после блоба;
- `fetchWithTimeout` сохранён для не-файловых запросов с жёстким лимитом.

### 2. Черновики в чате — строки для чтения, не формы

Оба черновика (наставник `renderMusicDraftContent` и продюсер `renderProducerDraft`)
раньше рендерили редактируемые `input`/`textarea` прямо в ленте — карточка выглядела
как форма и провоцировала правки в чате.

Теперь:

- `draftReadRow(label, text, {expandable})` — название одной строкой; описание звучания
  и лирика — сворачиваемые `<details>`-строки (тот же паттерн, что «Что уехало в модель»
  в карточке трека): превью до 120 символов, разворот кликом по строке;
- кнопка **«Копировать»** на каждой строке — целиком в буфер
  (`navigator.clipboard` + `execCommand`-фолбэк для не-secure context), тост
  «Скопировано в буфер обмена»;
- правки — только в «Тонко настроить» после «Принять в поля» (как сформулировал
  владелец: «в тонкой настройке если что-то не устраивает уже исправляется»);
- кнопки «Принять в поля» / «Вернуть как было» / «Сгенерировать трек» и вся логика
  бэкапов/откатов сохранены; валидации и запись полей читают значения черновика
  напрямую (`entry.draft` / `entry`), а не из инпутов карточки;
- в карточке наставника пропали input-листенеры и дебаунс-сохранение правок карточки
  в сессию (сохранять нечего — карточка только читается); `producerSaveTimer` удалён
  вместе с флэшем в `pagehide` (писателей больше нет).

## Красное / остатки

- **Локальный флак полного `check-studio` в песочнице**: на ~40-м браузерном контексте
  рендер умирает («Target page closed») в районе T-26 — **воспроизводится на родительском
  коммите (чистое дерево)**, т.е. это ограничение окружения (headless-shell, /dev/shm
  64M, медленный CPU), не регрессия. Изолированный прогон T-26 с правками #41 — зелёный.
  Гейт — CI ветки (ubuntu), по процессу репозитория.
- **Найдена и не закрыта гонка** (вне объёма #41): сохранение `advanced` в сессии
  асинхронной очередью IndexedDB гоняется с перезагрузкой страницы — после рестарта
  композер может вернуться в Simple, хотя ушёл в advanced. Тест теперь честно
  возвращается тумблером. Кандидат в отдельную задачу: флэш saveQueue в `pagehide`.
- Серверные причины «ошибки на каждый чих» (модерация 422, retention 404, 429) —
  клиент обрабатывает честно и с ретраями, но их источник в bff, не в студии;
  при желании — отдельный аудит сервера.
