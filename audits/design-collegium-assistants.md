# Дизайн-коллегиум: три целостных сценария «от идеи до готового трека»

Дата: 14.11.2026. Сессия: product-designer (конвейер ADR-0002, briix-studio).
Вход: `audits/audit-music-mode-interaction.md` (факты по коду), `audits/research-assistant-interaction.md` (15 рекомендаций + 5 анти-паттернов), жёсткие требования владельца (briix-studio#7), код `studio/studio.js`, `producer-brain.js`, `music-brain.js`, `studio.css`, `waveform.js`.
Формат: три ЦЕЛОСТНЫХ дизайна — сценарий, а не список фич. Правок кода нет; размеры изменений (S/M/L) — оценка по блокам studio.js. В браузере ничего не открывал — всё статически по коду.

## Общие факты, на которые опираются все три варианта

- Dispatch: `create()` (studio.js:696) безусловно ведёт любой текст music mode в `createMusic` — разговора в music mode нет.
- `ASSISTANTS.music` (Продюсер/Лирик/Автор песни, studio.js:36-40) — мёртвый UI: system-промпты нигде не отправляются.
- producer-путь `prepareMusic` (studio.js:1084) + карточка-черновик `renderProducerDraft` (:1134) — готовый паттерн «артефакт с явным принятием» (A5 ресёрча): поля, предупреждения, apply/revert с бэкапами.
- Прозрачность уже частично есть: `addMusicDetails` (:585) показывает «Промпт в модель» (`input.promptSent`, #109) и лирику.
- Волна: `waveform.js` — opt-in «Показать форму звука», 160 баров, canvas + отдельный range-слайдер; декод с жёсткими бюджетами (8 МБ файл, 60 сек, 32 МБ PCM). Требование владельца «волна = часть плеера» реализуется на его базе.
- Требования владельца (#7): обложка = PLAY, волна с кликом/перемоткой, единое меню «⋯», карточка трека = собранный компонент, наставники реально помогают.

## Общая анатомия карточки трека (входит во ВСЕ три варианта)

Требование #7 одинаково для A/B/C — различается только то, где карточка живёт (лента / диалог / панель работы).

```
┌──────────────────────────────────────────────┐
│ [▶ обложка 56–96px]  Название трека          │  ← обложка = кнопка PLAY (Spotify/SoundCloud):
│                      3:12 · Flash · Песня    │    клик по картинке = play/pause аудио
│                      волна █████▂▄█▆▂▃ 1:47  │  ← волна В плеере: canvas + невидимый
├──────────────────────────────────────────────┤    range-оверлей; клик по волне = seek
│ ▶ Скачать  ♥ Избранное              [⋯]      │  ← основные действия + единое меню
├──────────────────────────────────────────────┤
│ ▸ Что уехало в модель                        │  ← transparency (B3), details:
│   промптSent · модель · источник лирики      │    «написал пользователь / автолирика /
│   [показать промпт][показать лирику][копир.] │    наставник Продюсер», кнопки копирования
└──────────────────────────────────────────────┘
```

Меню «⋯» (одно вместо россыпи кнопок): Скопировать промпт · Скопировать лирику · Скачать · Повторить с правками · Создать обложку · В избранное/Убрать · Удалить (с confirm). Кнопка «Скачать» и «♥» остаются видимыми (частые действия), остальное — в меню.
Изменения кода: новый рендер `renderTrackCard(entry)` взамен разрозненных `addMusicActions` (:559) + `addMusicDetails` (:585) + inline-рендера аудио (:983-991 и feedRestore :332-334); `waveform.js` — авто-attach вместо opt-in кнопки, seek кликом по canvas (убрать дублирующий range-слайдер, оставить его как a11y-фолбэк). Обложка как кнопка play — S в JS (click → `audio.play()/pause()`, иконка ▶/⏸ поверх картинки), M в CSS. Существующие запасные механизмы сохраняются: budget-ограничения waveform.js, `audio.controlsList='nodownload'` → заменяется нашей кнопкой в «⋯».

Мобильный 390×844: карточка на всю ширину, обложка 56px, «⋯» открывается как bottom-sheet (существующий паттерн `.menu` + фиксация к низу); desktop: карточка до 640px в ленте, меню — popover у кнопки. Волна: на мобайле 56px высота, клик-зона ≥44px.

Правило [hidden] и цветовые токены не нарушаются: вся видимость через `hidden`, цвета — только существующие переменные (`--accent` уже используется waveform.js).

## Вариант A — «Явная развилка»: минимально-инвазивный

**Идея:** генерация остаётся главным путём одного send (как сейчас), но все молчаливые трансформации выносятся из тени, а наставники подключаются к СУЩЕСТВУЮЩИМ кнопкам. Ничего не перестраиваем — убираем анти-паттерны.

### Поток пользователя

1. Пользователь в music mode вводит «напиши мне стихи про осень» и жмёт send. **Видимая развилка появляется не ПОСЛЕ генерации, а до:** карточка-черновик «Продюсер подготовил» (тот же `renderProducerDraft`, :1134) с полями «Название / Звучание / Лирика» — НЕ джоба. send больше не молча создаёт дорогую джобу: он превращает текст в черновик наставника (дёшево, один `chatNonStream`, producer-brain.js).
2. В карточке-черновике: `brain`-теги и предупреждения — как сейчас; источник лирики подписан («лирику написал Лирик по вашей теме»). Кнопки: **«Сгенерировать трек»** (новая, рядом с «Принять в поля») и «Принять в поля студии» (как сейчас).
3. «Сгенерировать» → `createMusic` уже с готовым английским промптом черновика (без автолирики и без молчаливого перевода — они уже сделаны видимо). Молчаливые шаги createMusic (автолирика :920, translatePrompt :953) при этом пути пропускаются.
4. Правки: пользователь редактирует поля прямо в карточке-черновике и жмёт «Сгенерировать» снова — self-refine цикл через правки артефакта (дёшево, без LLM).
5. Результат — карточка трека (общая анатомия выше) с transparency «что уехало в модель».
6. Быстрый путь для уверенных пользователей: если пользователь включил «Тонко настроить» и заполнил поля сам — send работает как сегодня, сразу `createMusic` (без промежуточной карточки). Развилка видна в состоянии композера: под полем подпись «send = создать трек сразу» vs «send = продюсер подготовит черновик».

### Роль наставников

- Чип наставника в music mode становится РЕАЛЬНЫМ: выбранный наставник определяет system-промпт prepareMusic (сейчас там жёсткий producer-brain.js промпт, `BriixProducer.messages`). Продюсер — {title, prompt, lyrics} как сейчас; Лирик — только лирика с [verse]/[chorus] (заполняет поле «Лирика» черновика); Автор песни — полная лирика по теме + минимальный промпт. Все три возвращают артефакт в карточку с явным принятием.
- «Улучшить» в advanced-полях (`improveText`, :195) тоже получает system выбранного наставника вместо безликого «Ты редактор музыкальной студии».

### Изменения в коде (оценка)

- `create()` (:696) — ветка music: вместо безусловного `createMusic` → вызов `prepareMusic`-подобного потока, если поля не заполнены вручную. **M** (сохранение существующих сюит: ветка advanced-руками остаётся старым путём).
- `prepareMusic` (:1084) + `BriixProducer.messages` — параметризация выбранным наставником; return не JSON-черновика, а уже собранного entry. **S/M**.
- `renderProducerDraft` (:1134) — добавить кнопку «Сгенерировать трек» (вызывает `createMusic` c флагом «промпт готов, не трансформировать»). **S**.
- `createMusic` (:852) — флаг `snapshot.promptReady`: пропустить автолирику/перевод/brain-merge. **S**.
- Карточка трека (общая анатомия) — **M/L** (новый компонент + waveform.js правки).
- studio.css — карточка трека, меню «⋯», bottom-sheet. **M**.
- Сюиты: правки ожидаются на dispatch и на порядок вызовов при генерации (осознанно).

### Риски, плюсы/минусы

- **Плюсы:** минимальный риск регресса (producer-механика apply/revert/бэкапы уже отработана); снимает все 5 анти-паттернов почти бесплатно; два клика до трека.
- **Минусы:** send перестаёт быть «мгновенной генерацией» для Simple-пути (два клика вместо одного); разговор с наставником всё ещё НЕ диалог (одноразовый черновик — серии «поправь припев» невозможны); стоимость: средняя (M в dispatch + M/L карточка трека).
- **Риски:** привычка «жму send — сразу играет» ломается для части пользователей; qwen3:4b может вернуть не-JSON для Лирика/Автора песни — fallback на `BriixProducer.parse` обязателен; THREAD_BUDGET — один дополнительный вызов на черновик.

### Как НЕ нарушить анти-паттерны

- АП1: send больше не молча запускает дорогую джобу из произвольного текста — сначала видимая карточка-черновик, генерация отдельной кнопкой. Исключение — только когда пользователь сам заполнил поля (его явная сборка).
- АП2: чип наставника подключён к реальному system-промпту, каждый наставник производит артефакт (черновик с полями) с явным принятием.
- АП3: разделение дешёвого/дорогого: черновик = дешёвый `chatNonStream`; генерация = отдельная кнопка в карточке. Send в advanced-режиме = заведомо собранный промпт пользователя, не «догадка».
- АП4: автолирика/перевод/теги видны в карточке черновика с подписью источника; при promptReady-пути они не выполняются вовсе.
- АП5: одна активная роль на сессию (чип), метка роли в карточке («Лирик · черновик»); никакого «совета трёх наставников».

## Вариант B — «Студия-агент»: разговорный центр (Suno conversational)

**Идея:** в music mode главный send ведёт в ДИАЛОГ с наставником (как `createChat`, :705), генерация — явное действие из диалога. Аудит п.1/п.2 закрывается маршрутизацией, рекомендация A2/A5/B1 — это ядро.

### Поток пользователя

1. Пользователь в music mode пишет «хочу песню про осень, что-то тихое» → send → **диалоговое сообщение** наставника (создаётся chat-поток music-сессии). Наставник (чип: Продюсер/Лирик/Автор песни) видит контекст сессии: текущие `els.musicPrompt`, `els.lyrics`, instrumental, quality (B9 — как `prepareMusic`-snapshot) + историю диалога.
2. Наставник отвечает разговорно И производит артефакт: в конце ответа — **draft-блок** (промпт-строка англ. и/или лирика с тегами) с кнопками «Принять в поля» и «Сгенерировать трек». Метка роли на карточке («Продюсер»).
3. Пользователь: «а сделай припев жалче» → send (дёшево, тот же диалог) → Лирик правит точечно, draft-блок обновляется в новой карточке диалога. Self-refine цикл (B1): серии правок работают, потому что контекст диалога сохраняется.
4. «Сгенерировать трек» (кнопка на draft-блоке или явная кнопка «Создать» рядом с send, когда в сессии есть принятый draft) → `createMusic` с promptReady-флагом варианта A → карточка трека в той же ленте сессии (A6: диалог и джобы в одной сессии — session-store хранит и messages, и jobs).
5. После генерации диалог продолжается про этот трек: «сделай вариант без баса» → наставник готовит новый draft → новая генерация с parentJobId.
6. Второй явный путь сохранён: «Тонко настроить» — поля advanced, заполненные руками, send = сразу `createMusic` (как в варианте A; для тех, кто знает, чего хочет).

### Роль наставников

- Продюсер: разговор о стиле → артефакт «англ. промпт одной строкой + brain-теги»; Лирик: правки лирики точечно по диалогу; Автор песни: полная лирика из темы. Все — в формате draft-блока с явным принятием (не болтовня без артефакта). Контекст — snapshot полей + история диалога (обрезка до лимита qwen3:4b).
- Роль видна в каждой карточке диалога и в карточке трека («источник лирики: Лирик, 3 правки»).

### Изменения в коде (оценка)

- `create()` (:696) — в music mode: если advanced-поля заполнены руками → `createMusic`; иначе → новый `createMusicChat(text)` по образцу `createChat` (:705) c `currentAssistant().system` + snapshot-контекст. **M**.
- `createMusicChat` — новая функция (~80 строк): chatStream с историей, парсинг draft-блока из ответа (маркер-формат или JSON с fallback `BriixProducer.parse`), рендер draft-блока. **L**.
- Draft-блок — обобщение `renderProducerDraft` (:1134) до компактного inline-компонента с apply/«Сгенерировать». **M**.
- session-store.js — сессия music хранит messages (уже умеет для chat) + jobs; миграция старых сессий. **M**.
- Кнопка «Создать» в композере + `updateEnabled` (:655)/`renderChrome` (:627) состояния. **S**.
- Карточка трека (общая анатомия). **M/L**.
- Сюиты: dispatch-сюиты переписываются по задумке; chatStream/payload-сюиты; session-store миграция. Наибольший объём тест-правок из трёх вариантов.

### Риски, плюсы/минусы

- **Плюсы:** единственный вариант, дающий настоящий self-refine диалог («поправь припев» сериями); лучший ответ на требование «наставники реально помогают»; разговор и результат в одной сессии.
- **Минусы:** самая дорогая разработка (L в новой функции + M в session-store); серия правок на qwen3:4b — слабое качество длинного диалога, нужен жёсткий формат-контроль и обрезка истории; две кнопки в композере — риск путаницы.
- **Риски:** THREAD_BUDGET при длинных диалогах; формат draft-блока малая модель соблюдает нестабильно — парсинг с фолбэком на «показать ответ как обычный текст» (без draft-блока, только кнопка «Принять в поля» из ручного копирования); дрейф роли при смене наставника посреди диалога — сбрасывать историю-контекст при смене роли.

### Как НЕ нарушить анти-паттерны

- АП1: авто-маршрутизации намерения нет: развилка ДЕТЕРМИНИРОВАННАЯ и видимая — «поля заполнены вручную» → генерация, иначе → диалог (A3 ресёрча: авто-классификатор на qwen3:4b отвергнут сознательно).
- АП2: каждый ответ наставника содержит артефакт (draft-блок); роль подключена к реальному system-промпту.
- АП3: send = дёшево (диалог), генерация = отдельная явная кнопка на draft-блоке/кнопка «Создать» (B6).
- АП4: все трансформации (перевод, теги, лирика) — внутри диалога видимо; в promptReady-генерации молчаливых шагов нет; в карточке трека — источник лирики.
- АП5: одна роль на сессию, метки на карточках, смена роли вручную с очисткой контекста.

## Вариант C — «Верстак трека»: артефакт-центр (Udio-подобный)

**Идея:** центр интерфейса — не чат и не поле ввода, а **Верстак**: постоянная панель текущего трека (черновик → результат), к которой привязаны и наставники, и действия. Разговор обслуживает артефакт, а не существует рядом (A4: операции живут на артефакте).

### Поток пользователя

1. В music mode лента показывает последнюю активную «карточку работы» (Workbench card): на старте — черновик (поля Название/Звучание/Лирика + brain-теги), после генерации — карточка трека (общая анатомия), между ними — stage-полоса (существующий waitRow).
2. Пользователь вводит идею → она попадает в поля верстака (видимо, с подсветкой «из вашей идеи»), и выбранный наставник одновременно предлагает доработку: сбоку/снизу — компактный диалог-рейл с наставником (правки к СЕЙЧАСШНЕМУ верстаку, B9-контекст — сам верстак).
3. Правки лирики — прямо в полях верстака или через диалог («поправь припев» → Лирик присылает изменённый фрагмент с diff-подсветкой и кнопкой «Применить к верстаку» — явное принятие, как producer apply).
4. Кнопка «Сгенерировать» на верстаке (крупная, единственная дорогая кнопка экрана) → stage-полоса → карточка трека заменяет верстак; «Повторить с правками» из «⋯» возвращает трек на верстак как новый черновик (parentJobId).
5. История версий: каждый «Сгенерировать» оставляет предыдущую карточку трека в ленте сессии (как сейчас), верстак всегда работает с последней.

### Роль наставников

- Наставник привязан к верстаку, а не к полю ввода: его ответы всегда про текущий материал (diff-фрагменты лирики, вариант промпта). Продюсер правит «Звучание», Лирик/Автор песни — «Лирику». Все правки через «Применить» (explicit accept), diff-подсветка делает цикл self-refine наглядным.
- Роль-метка в диалог-рейле и в версии трека.

### Изменения в коде (оценка)

- Верстак — новый крупный компонент (объединяет `renderProducerDraft` + advanced-поля + карточку трека в одно состояние). **L**.
- `createMusic` — чтение из верстака вместо els-полей (или верстак пишет в те же els — тогда S). **M**.
- Диалог-рейл — `createMusicChat` из варианта B в сжатом виде. **L** (совместно с B-частью).
- Diff-подсветка лирики — новая утилита (~60 строк, без библиотек). **M**.
- Карточка трека (общая анатомия). **M/L**.
- studio.css — верстак, рейл, diff. **L**.
- session-store — как в B. **M**.

### Риски, плюсы/минусы

- **Плюсы:** самый цельный ответ на требования #7 (карточка = собранный компонент, центр экрана); лучший для iterative-пользователей; diff делает принятие решений быстрым.
- **Минусы:** самая дорогая разработка (два L-блока + крупный CSS); ломает текущую ментальную модель «лента + композер» сильнее всех; риск перегруза UI на 390×844 (верстак + рейл + лента — на мобайле рейл сворачивается в отдельную вкладку, что удваивает навигацию); больше всего новых сюит.
- **Риски:** дифф на слабой модели может быть шумным (модель переписывает больше, чем просили) — diff обязателен, иначе доверие падает; два L-компонента в одном релизе — нельзя, только поэтапно (верстак без рейла, рейл вторым релизом).

### Как НЕ нарушить анти-паттерны

- АП1: идея пользователя попадает в верстак ВИДИМО (подсветка полей), генерация — только кнопка верстака; никакого автоматического запуска.
- АП2: наставник производит фрагмент-артефакт с кнопкой «Применить» (явное принятие); чип подключён к system-промпту.
- АП3: «Сгенерировать» — единственная дорогая кнопка, физически отделена от ввода и от диалога (send диалога — дёшево).
- АП4: brain-теги/перевод/автолирика — видимые подписи в верстаке; promptReady-путь без молчаливых шагов; transparency в карточке трека.
- АП5: один наставник на верстак, метки ролей; смена — вручную.

## Вопросы владельцу (максимум 3)

1. **Главный сценарий музыки — быстрый или итеративный?** Если пользователи чаще хотят «из идеи в трек за 1–2 минуты» — берём **A** (два клика, минимум риска). Если ценность в совместной доводке («поправь припев», серии правок) — берём **B**.
2. **Бюджет разработки: один релиз или конвейер?** Если нужен один законченный релиз с минимальными правками сюит — **A**. Если готовы переписать dispatch- и session-store-сюиты ради диалога — **B**. Если готовы на два L-релиза поэтапно — **C**.
3. **Судьба одного send в music mode:** если send должен остаться «создать трек» (привычка текущих пользователей, сюиты dispatch) — это **A**. Если send = «сказать наставнику», а генерация — отдельная кнопка — это **B/C**. Это решение нельзя принять за владельца: оно меняет смысл главной кнопки студии.
