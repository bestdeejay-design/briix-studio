# BRIIX-STUDIO-PROJECT — адаптация канона под репозиторий студии

> Проектный слой поверх снимка канона (`docs/agents/PROTOCOL.md`, `WORKFLOW.md`).
> Ничего нового не вводит — только применение существующих правил к briix-studio.
> При расхождении с каноном канон старший (PROTOCOL §3: казус → письменное правило).

## 1. Продукт и границы

- **Продукт:** BRIIX Студия — SPA (`studio/`), мозги (`producer-brain.js`, `music-brain.js`),
  статик без сборки. Правила продукта — `README.md` и серверный контракт `server-contract/`.
- **Прод:** https://demo.briix.ru/studio/ (деплой CI из main: tests → deploy-stand).
- **Святые зоны студии** (аналог PROTOCOL §2 «замороженных»):
  - правило длительности: **длительность трека никогда не уходит модели** (динамическая длина);
  - промт модели — **только английский**, теги секций `[Verse]/[Chorus]…` латиницей;
  - лирика по умолчанию английская, русская — только по явному слову пользователя;
  - битрейт-матрица mux: flash→192k, pro→320k, instrumental→всегда 320k;
  - теги M4A: title + artist=ник профиля, имя файла через `safeFileName`.
  Правка этих зон — только по явному слову владельца через issue.

## 2. Ветки и поставки (канон WORKFLOW §2)

- `main` пишет только координатор. Ветка исполнителя: `arena/<id-сессии>-briix-studio`
  или `fix/<slug>`/`feat/<slug>` — у каждой задачи своя, база от свежего `origin/main`.
- Ветка удаляется сразу после мержа PR (`gh pr merge --delete-branch`).
- Письмо о поставке (WORKFLOW §3) в студии живёт как отчёт в `audits/task-<N>-<slug>.md`
  + описание PR: что сделано, как проверено, что красное, диапазон коммитов.

## 3. «Полный регресс» студии (канон WORKFLOW §4 ч.4)

Канонический список сюит (гонять все, не выборочно), `NODE_PATH=/opt/homebrew/lib/node_modules`:

```
node tools/check-studio.cjs          # 73+ ассертов, сквозные сценарии
node tools/check-assembly.cjs        # санитизация, язык, латинские теги
node tools/check-session-store.cjs   # IndexedDB: миграция, бэкап, изоляция, CAS
node tools/check-session-migration.cjs # schema v1→v2 в точке загрузки (#35: merge истории, pending-ключ, гейты)
node tools/check-export.cjs          # экспорт v1 (#35): WAV/M4A/обложка, честная деградация, ?refetch=1
node tools/check-studio-storage.cjs  # интегрированный fallback
node tools/check-waveform.cjs        # волна из пиков, 0 AudioContext
node tools/check-producer.cjs        # продюсер-парсинг и лимиты
node tools/check-music-brain.cjs     # DJ1-теги
node tools/check-wait-phrases.cjs    # фразы ожидания
node tools/check-a11y.cjs            # axe, 0 serious/critical
node tools/asset-versions.cjs        # отпечаток сборки (после правки ассетов: --fix)
node tools/check-cache-selfheal.cjs  # кеш-сторож (chromium)
```

Гейт поставки, меняющей формат данных (канон PROTOCOL §7): тест на **реальных данных
владельца** — репродукция на копии профиля в живом браузере, не только синтетика.

## 4. Size-классы студийных задач (канон WORKFLOW §6.1)

- **S (Fast-Track Дуэт):** точечный guard, правка текста/стилей одного файла, тест.
  Примеры дня 16.11: отпечаток сборки (#26), guard одного поля.
- **M (коллегия, 2 волны):** формат данных/миграция, новый механизм в одном модуле.
  Пример: санитизация session-store (#25/#27) — это была M (формат, оба бэкенда, CAS).
- **L (коллегия + ADR + SPEC_PACK):** новый режим UI, смена контракта сервера.
  Пример: вариант B «Студия-агент», перенос студии в отдельный репо.

## 5. Карточки борда (канон WORKFLOW §8.1 + BOARD.md)

- Карточка в GitHub Projects (issue + поля «Сессия», «Этап поставки») — **до старта**
  любой задачи, включая S. Работа без карточки не признаётся и не деплоится.
- После приёмки — комментарий на issue: что и как реализовано (файлы, механизм,
  проверки, остатки), чтобы причина читалась на карточке, а не искалась по диффам.

## 6. Сабы координатора (канон PROTOCOL §8 + ADR-0002)

- Одна миссия = один свежий саб. Переиспользование исполнителя/ревьюера между
  задачами дня запрещено: накопленный контекст убивает независимость проверки.
- Ревьюер всегда не автор. Ни один коммит не аппрувится его автором (волна 2).
- В промпт саба включаются нужные skills (браузер для живой проверки, деплой и т.д.).
- Разделение верификации в брифе (PROTOCOL §8): исполнитель проверяет код/тесты,
  координатор — живой прод (репродукция в браузере, деплой, данные владельца).

## 7. Кеш и деплой-гигиена студии

- `index.html` студии содержит кеш-сторож (`__BRIIX_BUILD__` + `version.json`):
  правка любого ассета требует `node tools/asset-versions.cjs --fix` **до** PR —
  рассинхрон отпечатка красит CI на main (проверка T-35).
- Инфра-правки (Caddy, стенд) — только через INFRA issue, не в этом репо
  (пример: briix-studio#23 → infra#113).

## 8. Канал арены

- Задание — issue; отчёт — файл в `audits/` + PR. У интеграционного токена нет
  `issues:write` (комментарии в issue из CI не пишутся) — канал односторонний.
- Конфликты ветки арены с main разрешает арена (перебазирование), не координатор.
